# 全局 Agent 规则（DSH）

> 规则源在仓库 `dsh/global-rules.md`，安装到 `~/.dsh/AGENTS.md`：改了源要重跑 `scripts/install.sh` 才生效。
> 它刻意不叫 AGENTS.md——名字一旦叫 AGENTS.md，在仓库里干活时它会被同时当成项目级指令再注入一遍，白烧一份上下文。

## 通例

- 默认简体中文；代码标识符、命令和路径保持原文。
- 结论先行。最终答复保留结论、关键证据、验证、剩余风险和必要下一步，省略过程复述。
- 以当前机器、仓库、会话和真实运行表面的证据为准。
- 做能解决问题的最小 diff：先删除再添加，不引入目前无人需要的层次、选项或辅助函数，不覆盖或还原用户已有改动；只有一个调用方就别抽象，直接内联。
- 编辑前先读要改的代码；改函数行为前先找齐全部调用方。
- 每次行动前用一行话复述任务：目标是什么，预计的最小改动是什么。
- 控制上下文：只读需要的局部，留摘要不留原始输出；不重读刚改过的文件，不重复已经做过的搜索。
- 讲给用户听时，当他是个愿意学的新手：先给比喻，再补必要的专业术语。

### 务实原则

- 测试只为验证这次改动本身，不穷举世界上的所有可能。
- 代码够用就好，不给现实中不会出现的输入写防御。
- review 只认现实：结合项目实际用途、规模和运行环境判断严重性。判据是两个问题——现实里真的会碰到吗？真碰上了后果严重吗？两个都不沾边就列为建议，不当问题修；只报能在本项目里复现的，拿不出复现路径的最多写成建议。
- 同一方案失败两次就停：把两次失败的共同假设写下来直接检验，不换第三种变体硬试。

### 留存的铁律

需要设计取舍或系统化调试时，读 `~/.dsh/rules-design.md`（17 条；仓库内是 `dsh/rules-design.md`）。下面几条常驻：

- 先删减，再少量新增：先清掉无用代码和过期检查，再做能工作的最短 diff。
- 在边界设防：CLI、配置、网络、文件、外部 API 的入口处校验；系统内部信任类型，核心逻辑保持纯粹。
- 先迁移，再删除：一次改动里迁移全部调用方并删掉旧 API，不留兼容层。
- 解决根本原因：在状态首次出错的位置修，防护逻辑只处理合法状态。
- 步骤幂等：重复运行一步，崩溃后重跑也能到达同一状态。
- 避免共享写入者：用锁之前，先让每个并发执行者拥有自己的文件、分支或键。
- 构建工具：批量或重复的检查写成可重复运行的脚本。

## 边界与确认

- 只要回答、解释、分析、诊断、review 或规划：检查材料、报告结果，不改代码或外部状态。
- 要求修改、实现、构建或修复：完成范围内的本地改动和非破坏性验证，无需重复确认（commit / push / PR 见「本机约定」）。
- 外部系统写入、发送或发布、破坏性操作、付费、权限变更前必须确认。
- spec promotion 只在知识稳定、可复用、已验证且用户确认后执行。

## 流程与入口

- 路由优先级：明确属于 Inline 的简单任务直接处理；其余工程任务走 Matt 方法。
- Inline：只读问答、代码解释、局部配置或文案、单文件或根因明确的小修。直接处理加最小验证，不建 Trellis task。
- Matt：按当前可用 skill 的 description 路由需求拷问、PRD/issue、实现、TDD、诊断、review、架构和 research；这里不复述完整 skill 清单。
- Trellis：已进入 Trellis 生命周期的任务，由它管任务状态、planning artifacts、spec/research、跨会话恢复和 archive；细节以项目 workflow 和 Trellis skills 为准。一个阶段只保留一个 workflow owner。
- 进 Trellis 的门槛：需要多决策、跨会话、要留 planning artifacts 才进；简单工作不建 task。
- plan 闸门：建任务、写 spec/tickets 或进入 Trellis planning 之前，先加载 `grill-with-docs`（在仓库里工作时优先；等价的是 `grill-me` / `grilling`），把需求、范围和关键决策聊清楚并达成一致，再产出 plan。顺序是先 grill、后建任务，Matt workflow 的 1.0 建任务也按这个顺序。
- 项目里没有 `.trellis/` 这类长期记录设施时，不主动初始化，除非用户明确要求。

### DSH × Trellis 入口

- DSH 是 pull 型宿主：当前 Trellis 不给 dsh 安装 session hook，也没有等价的自动注入。所以进入含 `.trellis/` 的项目后，每个新会话先加载 `trellis-start`（它读当前任务状态并路由），不凭记忆猜阶段。
- `trellis-start` 是每个会话的固定入口，它只做路由，不等于要建任务：Inline 小修照样加载完直接做。
- 续做已有任务加载 `trellis-continue`；收尾/归档加载 `trellis-finish-work`。

## 派子代理

选用 research、code-review、implement-spec 这类以子代理为前提的 skill，或运行 workflow 时，视为已明确选用并行执行，不需要再确认：并行派子代理不算扩张范围，是「边界与确认」里的既定例外。

- 提示词写全：背景、问题、任务，以及相关文件和参考项目的完整路径。
- 要求它编写临时验证脚本完整复现逻辑；既看改动本身，也看有没有弄坏原有功能、需求是否真的达成。
- 提示词里写明：只自己干，不再派子代理。
- 提示词里带上「务实原则」的判据：只报现实里真会发生的问题。
- 它跑的时候只做自己的独立审查，要说的话等它回来；不 sleep、不反复轮询，继续做独立审查或直接结束本轮，完成会自动通知。
- 回来之后：先核实它报的问题是否真实存在，再校对严重性和评级，然后用大白话讲给用户听，先不动手。
- 它提了 p0/p1：修完再叫一个新的子代理看一轮，直到没有阻塞级问题才收手。这个循环算本次审查的授权范围内，不算擅自叫；审查收手之后再改别的东西，想再叫要重新问用户。

## 本机约定

- 宣称完成、通过、可提交或可合并前，先跑真实对象、读真实输出；没有直接验证证据就不说这些结论。
- commit message 默认 `<type>(scope): <中文动词短语>`，不加句号。
- commit、push、PR 只在用户明确要求时执行。
